What's actually happening under the hood

The IBAN checker implements the real ISO 7064 MOD 97-10 checksum algorithm — the same verification international banking systems use — not a lookup against known examples. It converts letters to numbers (A=10 … Z=35), rearranges the string per the standard, and computes an exact modulo-97 check using native BigInt arithmetic so precision isn't lost on the very large numbers involved.

Does a valid checksum mean the account actually exists?

No. A passing checksum only confirms the IBAN is internally well-formed — it catches typos, transposed digits, and copy-paste errors, which is the vast majority of real-world IBAN mistakes. Confirming the account is open, active, and belongs to who you think it does requires the receiving bank's own verification, not a client-side format check.

Why does the mobile lookup say "originally assigned" instead of just naming the network?

Since Mobile Number Portability launched in Pakistan, a subscriber can switch operators while keeping their number, so the prefix reflects who the number was first issued to by PTA — not necessarily who's carrying the call today. For anything where the live carrier actually matters (SMS delivery routing, for instance), that has to be confirmed with the telecom itself, not inferred from the prefix alone.

Why doesn't the CNIC checker validate against NADRA?

Unlike IBANs, CNIC numbers don't have a publicly documented checksum digit — the 13th digit is not a self-verifying check digit the way a credit card or IBAN's is. This tool only confirms the input has the correct digit count and formats it into the standard XXXXX-XXXXXXX-X pattern. Confirming a CNIC is genuine requires NADRA's own verification systems, which this tool intentionally does not attempt to replicate or bypass.
